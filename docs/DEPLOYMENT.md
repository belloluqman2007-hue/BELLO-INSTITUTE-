# Deployment

This platform is deployed as a **brand-new service**, independent of the old
production deployment (the old service identities are inventoried and
delisted in `ISOLATION-AUDIT.md`). Nothing in this repo points at, proxies
to, or reuses the old deployment. You create a *new* service and fill in
*new* values.

## Target: Render (recommended)

`render.yaml` defines a single web service. It is intentionally minimal and
contains **no live secrets** — secrets are generated or set in the dashboard.

### Steps

1. **Create the new database** (see `DATABASE.md`) and note its connection
   string.
2. In Render, create a **new** Web Service from this repo (do *not* open or
   modify the old service). Enable **Blueprints** so `render.yaml` is read.
3. When prompted, provide the values marked `sync: false` in `render.yaml`:
   - `DATABASE_URL` — the NEW connection string
   - `SUPER_ADMIN_PASSWORD` — a strong, new password
   - `PUBLIC_URL` — the new service URL Render assigns
4. `SESSION_SECRET` is auto-generated by Render (`generateValue: true`).
5. Deploy. On first boot the service runs migrations, creates the fresh
   schema, and seeds the single super-admin from `SUPER_ADMIN_USERNAME` /
   `SUPER_ADMIN_PASSWORD`.

### render.yaml env vars (what each does)

| Key | Source | Notes |
| --- | ------ | ----- |
| `NODE_ENV` | fixed `production` | enables production validation |
| `DATABASE_DRIVER` | fixed `mysql` | use the new MySQL DB |
| `DATABASE_URL` | you set (`sync: false`) | NEW DB only |
| `SESSION_SECRET` | Render-generated | 32+ chars, required in prod |
| `SUPER_ADMIN_USERNAME` | fixed `admin` | change after first login |
| `SUPER_ADMIN_PASSWORD` | you set (`sync: false`) | strong, new |
| `PUBLIC_URL` | you set / Render-assigned | new domain |
| `LOGIN_RATE_LIMIT` / `API_RATE_LIMIT` | sensible defaults | |

### Resetting the super-admin password

`SUPER_ADMIN_PASSWORD` is only read **when the super-admin account is first
created** (first boot of a fresh database, or `npm run seed`). Changing the
env var afterwards — e.g. in Render → Environment — does **not** update the
password already stored in the database, and seeding intentionally skips an
existing super admin so a password the admin later changed in the app is
never silently overwritten. That is the most common cause of
"Invalid username or password" after "I already set the password in Render".

To make the account match the value currently in the environment, run the
explicit reset command against that database:

- **Render:** open the service's **Shell** (or `render shell <service>`) and
  run `npm run reset-admin-password`
- **Anywhere:** `npm run reset-admin-password` with the env vars of the
  target environment

The command sets the super admin's password to the current
`SUPER_ADMIN_PASSWORD` value (and creates the account if it does not exist
yet). No restart is required — just log in again. Note the username is
stored exactly as configured (default: `admin`, lowercase).

You can check the account exists in your database with:

```sql
SELECT id, username, role FROM users WHERE role = 'super_admin';
```

## Production validation (fail-fast)

`server/config.js` refuses to boot in production if any of these are wrong,
so a misconfigured deploy can never silently reuse another database:

- `SESSION_SECRET` ≥ 32 chars and not the template value
- `SUPER_ADMIN_PASSWORD` not the template value
- MySQL configured via `DATABASE_URL` or the four `DB_*` vars

## Other hosts

The app is a standard Node/Express server and runs on any Node ≥ 22 host
(Railway, Fly, a VPS, etc.). The contract is: set the same env vars from
`.env.example` (new values only) and run `npm start`. There is no
host-specific config baked in.

## What is NOT done here

- No real payment gateway is connected.
- No automatic migration of old data is performed (by design — the old data
  stays in the old system; migrate only if/when explicitly requested).
