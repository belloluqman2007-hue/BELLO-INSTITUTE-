# Report Sheet / Report Card System

The printable report is generated by **one engine** — `server/services/report-sheet.js`
— used by the staff workspace, bulk class generation, the student portal, the parent
portal and the public result checker. It does **not** re-implement any result
mathematics: totals, grades, grade points, averages, positions and promotion decisions
come from the existing trusted engine in `server/services/grading.js`, which remains the
only writer of `term_summaries`.

## Flow (unchanged lifecycle, one new surface)

```
results (gradebook) → submit → review → approve → compute → publish → portal/public access
                                                        ↘ report sheet preview/print/bulk (staff, any stage)
```

- The **review workflow** (draft → submitted → under review → returned/approved →
  published → locked) is untouched and still enforced by `routes/results.js`.
- **Students and parents only ever see published reports.** The portal endpoints check
  `term_summaries.published_at` server-side; portal result listings show published terms
  only and never include non-approved subject rows.
- **Corrections to a published/locked report** go through the existing authorised path:
  `results.publish` permission → `unpublish`/`unlock` (each audited) → correct →
  re-approve → republish. Ordinary users can never edit a frozen result.

## What the sheet contains

Everything is dynamic, from the institution's own data:

- **School identity**: logo (fallback monogram), name (EN + AR), motto, address, phone,
  email, website, brand colour. The platform never substitutes its own branding for the
  school's; "Powered by EduSphere" appears in the footer only when the institution
  enables it.
- **Student identity**: name (EN/AR), admission number, student code, class, gender,
  date of birth, section/program where present, photograph where uploaded (only
  `/uploads/...` paths are ever used as image sources).
- **Subjects**: the subjects actually assigned to the class with approved/published
  results — Islamic and Western institutions use the same engine because subjects are
  data, not code.
- **Columns** (configurable): CA, Exam, Total, %, Grade, Grade point, Remark, with
  configurable CA/Exam column labels and the institution's CA/exam maxima in the header.
- **Overall performance**: subject count, total, average, overall grade, position
  ("1st of 28"), class size and class average — aggregates only, never another
  student's marks.
- **Attendance**: present/absent/late breakdown and percentage from the real attendance
  records; an honest empty state when none exist.
- **Behaviour/conduct**: the institution's configurable categories with 1–5 ratings
  (stored on `term_summaries.behaviour_ratings`).
- **Comments**: the actual saved teacher and head comments.
- **Promotion**: the computed status, plus optional manual decisions
  (promoted-on-trial / withdrawn / completed).
- **Next term**: begins/ends from the academic calendar (next term in the session, else
  the first term of the next session).
- **Signatures**: configurable blocks (title, Arabic title, printed name).
- **Reference number**: deterministic `EDU-<session>-<class>-<admission>` value stored
  on `term_summaries.report_reference`; internal database ids are never printed.

## Configurable template

Stored per institution in the existing `settings` table under `report_template`
(no new settings system). A professional default means a new institution needs no
setup. An administrator (permission `report_cards.templates`) can configure:

layout (classic / modern / compact) · orientation (auto/portrait/landscape — auto
switches to landscape for wide subject tables) · brand colour · result columns ·
CA/Exam labels · section visibility (position, attendance, behaviour, comments,
promotion, class performance, student details, photo, next term, grading legend,
reference, watermark, credit line) · watermark text · behaviour categories ·
signature blocks.

`GET /results/report-template/preview` renders the configuration with clearly-marked
**sample data**, so no institution's real students are ever used in a preview.

## Endpoints

| Endpoint | Who | What |
| -------- | --- | ---- |
| `GET /api/results/report-sheet/:studentId/:termId` | staff (`report_cards.view`, teacher class scope) | full sheet dataset incl. status + completeness |
| `GET /api/results/report-card/:studentId/:termId` | staff | printable HTML (preview = print output) |
| `GET /api/results/report-cards/bulk?classId=&termId=` | staff (`report_cards.generate`) | whole class, one page per student |
| `GET /api/results/report-completeness?classId=&termId=` | staff | missing / awaiting-approval results |
| `GET/PUT /api/results/report-template` | view: staff · save: `report_cards.templates` | template configuration (audited) |
| `GET /api/results/report-template/preview` | staff | sample-data preview |
| `GET /api/portal/report-card?termId=&studentId=` | student (own) / parent (linked child) | published reports only |
| `GET /api/public/results/report/:token` | verified public checker | published reports only |

## PDF and printing

The platform's document pipeline (ID cards, certificates) renders HTML and produces
PDFs through the browser's print dialog; the report sheet uses the same pipeline.
This is deliberate: it preserves Arabic text shaping, RTL layout, school branding,
table page breaks and works on mobile and desktop without a server-side PDF binary.
The print CSS uses real A4 `@page` rules, repeats table headers after page breaks,
never splits a row across pages, and hides all application chrome.

## Database

Migration `038_report_sheet_system` adds two columns to the existing
`term_summaries` table (`behaviour_ratings`, `report_reference`) and two indexes for
the class-term lookups. It is dialect-aware (SQLite and MySQL) like every other
migration. No new tables.

## Security

- The results router is staff-only: student/parent roles are refused outright (they
  have their own portal endpoints) — this closed a pre-existing IDOR where a student
  could read a classmate's report data through `/api/results/report-card-data/...`.
- Every endpoint re-derives the tenant from the session, never from the request.
- Cross-tenant ids answer 404 (existence is not leaked); teachers are limited to their
  assigned classes; parents to their linked children.
- Report view / print / bulk / template / portal actions are written to the existing
  audit log (`report.*` actions).
